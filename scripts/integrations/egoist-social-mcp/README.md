# Egoist Social MCP

Единый локальный MCP для исследований Telegram, X и Instagram через существующие аккаунты Egoist Relay. Telegram использует клиент приложения; X и Instagram — принадлежащие приложению фоновые представления. Экспорт и задания сохраняет отдельный Node-сервис.

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| `social_status` | Состояние сервиса, очередей и доступности приложений |
| `social_capabilities` | Фактически доступные платформы и операции |
| `social_submit` | Поиск, чтение, история, экспорт и скачивание; возвращает ID задания |
| `social_job` | Состояние, количество, файлы, покрытие и курсор конкретного задания |
| `social_cancel` | Отмена своего задания с сохранением принятых данных |
| `telegram_join_chat` | Вступление в одну выбранную пользователем группу по handle/invite |

Telegram: `discover`, `chat_info`, `read`, `search`, `channel_history`, `chat_export`, `download`, отдельный `join_chat`. X: `discover`, `profile`, `read`, `search`, `channel_history`, `chat_export`, `download`, `article`, `read_thread`. Instagram: `discover`, `profile`, `read`, поддерживаемые режимы `search`, `channel_history`, `chat_export`, `download`, `read_thread`.

`transcribe` скачивает наблюдаемое поддерживаемое аудио/видео выбранных постов и обрабатывает его локальным Whisper. До 20 источников и 20 аудио/видео на задание; `language: "auto"` либо код языка, например `ru`. Результат: `transcripts.jsonl`, текст с временными метками и manifest с хешем медиа, моделью и полнотой. Время, точность и неполная обработка указываются явно. Фотография, ролик без звука или тишина не объявляются распознанной речью; недоступный runtime не устанавливается автоматически.

`channel` задаёт выбранный профиль/чат/канал для истории и экспорта; `url` либо `urls` задают конкретные посты. `read_thread` требует одну точную ссылку на запрошенный DM-диалог. Для Telegram доступны `topicId` и интервал `after`/`before` в Unix-секундах. Экспорт: `exportFormats: ["jsonl", "markdown", "html"]`, медиа: `includeMedia: true`. Результат сообщает доступность конкретной операции: наличие её имени в схеме не доказывает доступ к любому аккаунту или источнику.

## Результаты и ограничения

Файлы сохраняются в настроенном workspace: `Материалы/Социальные исследования/<jobId>`. `records.jsonl` содержит наблюдаемые поля, источник и время извлечения. Manifest сохраняет выбранный источник, фильтры, привязку к аккаунту, покрытие и курсор. Для медиа сохраняются проверенные размер и SHA256. Прерванный поток оставляет `partial-manifest.json`, принятые записи, фрагменты текста и незавершённые `.part` файлы. Незавершённое медиа не объявляется готовым.

До 100 записей на страницу, 1000 на задание, 300 секунд на задание; больший объём продолжается отдельным заданием с проверенным курсором. До 32 MiB JSONL, 1 GiB на медиа и 2 GiB медиа на задание при сохранении 1 GiB свободного места. У каждой платформы своя последовательная очередь; три платформы могут работать параллельно. Лимиты сервиса и фактическая полнота DOM/API остаются видимыми. HLS/blob/DRM и оплачиваемые режимы поиска требуют отдельной поддерживаемой реализации.

Сервер не отправляет сообщения, не публикует, не ставит реакции и не изменяет аккаунты. Вступление в выбранную Telegram-группу — отдельная операция. Открытие запрошенного личного диалога может изменить его обычный статус прочтения.

## Подключение и диагностика

В Codex используется регистрация `egoist_social` с Node 24 и `src/research/mcp.mjs`. MCP stdio запускает общий локальный сервис при необходимости; закрытие stdio не закрывает Relay. Локальный app bridge подтверждает сервер через HMAC и привязывает задания к исходному аккаунту. Смена аккаунта останавливает старое задание вместо сбора под новым аккаунтом.

Когда обычное окно Relay закрыто, сервер может запустить проверенную новую сборку в режиме `--research-headless`. Для этого нужен приватный install manifest с версией, протоколом и SHA256 установленного EXE. Старые сборки таким способом не запускаются. Наличие уже работающего экземпляра исключает запуск второго владельца сессий. Режим приложения скрывает окна; обычное открытие пользователем может показать этого же владельца.

Relay 1.4.1 поддерживает восстановление вспомогательного процесса внутри текущего владельца. Проверенный install manifest явно разрешает фиксированную пару `--research-headless --research-recover-existing`: кратковременный контроллер передаёт запрос существующему экземпляру и завершает работу. При неудачной передаче он выходит до инициализации аккаунтов. Проверяются исходные PID и время запуска; повторные попытки ограничены. После сбоя helper создаются новый runtime и токен, а операции старого runtime не воспроизводятся. Установка обновлённого EXE и загрузка его в приложение являются отдельным этапом; открытая старая версия не обновляет native-команды в памяти.

Пример локальной диагностики:

```powershell
& "$env:USERPROFILE\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe" scripts/research-service.mjs status
```

`app_owned_bridge_unavailable` означает, что текущая сборка приложения не предоставляет мост. Это состояние отличается от отсутствия авторизации. Новые native-команды требуют сборки Relay с этим мостом; старый EXE не загружает их динамически. Исходники, сборка, изолированный транспортный тест и реальный тест авторизованных аккаунтов подтверждаются отдельно в отчёте внедрения.
