# Мост Telegram: разбор падений (13.10.2026, Sennit 1.8.3)

Источник: независимый разбор (architect_fable, только чтение) по журналу `%LOCALAPPDATA%\com.egoist.relay\logs`, системному журналу Windows и экспериментам на Node 24 (скрипты во временной папке сессии, в проект не входят).

## Вывод

Супервизор (`tauri/src/telegram_transport.rs`) восстанавливает мост правильно: внутри живой сессии 2 из 2. Шесть «падений» из журнала:

| Случаи | Причина | Статус |
|---|---|---|
| 04.10, 05.10, 08.10 18:16Z, 09.10 | Перезагрузка Windows: журнал приложения в UTC, событие System 1074 «Перезапустить» совпадает до секунды. Node гибнет раньше родителя, супервизор успевает написать WARN | проверено |
| 11.10 18:13Z | Внешний `taskkill /F /IM node.exe` (субагент Claude); мост восстановлен за 1 с | проверено |
| 08.10 15:40Z | Оба Node-процесса умерли вместе; источник kill не найден | наблюдение |

Повторный bind на тот же порт после `TerminateProcess` проходит за 250–400 мс (эксперимент), так что гипотеза «порт занят» опровергнута.

## Реальные дефекты

| # | Где | Дефект | Статус |
|---|---|---|---|
| T1 | `scripts/telegram-transport.mjs:74-97` | Между `'upgrade'` и `handleUpgrade` сырой сокет ждёт `await openProxy()` без обработчика `'error'`. RST от клиента или смерть процесса WebView2 → `Unhandled 'error' event: ECONNRESET`, exit 1 | воспроизведено экспериментом, в журнале пока не встречалось |
| T2 | `scripts/telegram-transport.mjs` | Нет `uncaughtException`/`unhandledRejection` → причина падения не пишется | по коду |
| T3 | `tauri/src/telegram_transport.rs:198` | `stderr(Stdio::null())`, в WARN нет кода выхода, неудачные попытки не логируются | по коду |
| T4 | `src/lib/gramjs/extensions/PromisedWebSockets.ts:322-353` | При гонке маршрутов отказ проигравшего Lagom не записывается (`recordFailure`) → проба Lagom не планируется, до конца сессии Telegram ходит прямым маршрутом; если прямой заблокирован — секунды без связи | по коду |

## План

1. T1: `socket.on('error', destroy)` сразу в `'upgrade'`, снимать после передачи в ws или `end()`.
2. T2: обработчики `uncaughtException`/`unhandledRejection` → одна JSON-строка в stderr (без url и токена) и `exit(1)`.
3. T3: stderr в пайп, поток-читатель с лимитами, редакция токенов и hex ≥32, `log::warn!`; код выхода и причины неудачных попыток в журнал; молчаливый выход при штатной остановке.
4. T4: отказ Lagom в гонке → `routeHealth.recordFailure('lagom')`, проигрыш по abort отказом не считается.
5. Тесты: RST во время ожидания Lagom не убивает мост; редакция; гонка помечает Lagom.

*Приёмка:* `taskkill /PID <node моста> /F` → в журнале WARN с кодом выхода, «restored» ≤ 1 с, через ≤ 60 с Telegram снова на Lagom; в журнале нет 64-hex токена.

## Вне проекта

`taskkill /IM node.exe` без PID убивает мост Telegram и research-помощник. Стоит запретить такую команду в защите агентов (`EgoistCODEX AI/hooks/guard.py`) — решение владельца.
