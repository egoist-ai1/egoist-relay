## 1. Контекст: почему это важно именно сейчас

- Telegram в РФ: с 10.02.2026 Роскомнадзор официально подтвердил замедление; тяжелее всего страдают фото, видео, голосовые, текст проходит. Звонки закрыты с августа 2025 [проверено: https://en.wikipedia.org/wiki/Blocking_of_Telegram_in_Russia, на 17.03.2026]. Полного блока на 06.10.2026 нет; РИА Новости пишет, что Web открывается, медиа грузятся плохо [вторично: https://ria.ru/servisy/telegram-web-kak-voyti/]. Один справочный сайт сообщает недоступность web.telegram.org с 4 адресов в сентябре — расходится с РИА, зависит от оператора [вторично, спорно].
- MTProxy/Fake-TLS деградирует: с 01.04.2026 массовые отвалы, версия «DPI научился видеть Fake-TLS» [проверено как публикация, причина не подтверждена: https://www.securitylab.ru/news/571087.php]. Замер «Теплицы» 27–31.05.2026, 4 региона, 6 сетей: из 27 конфигураций рабочих 3; МТС, Yota, Инфолинк — 0 [вторично, цифры из выдачи; сама статья по сети не открылась: https://te-st.org/2026/06/02/mtproxyout/]. Habr: DPI ловит по JA3/JA4 и статистике потока, нестандартные порты не помогают; VLESS по тем же публикациям тоже распознаётся с декабря 2025 по май 2026 [проверено, но это мнение автора: https://habr.com/ru/articles/1041486/].
- X: Nitter и XCancel закрыты после претензий X (август–сентябрь 2026), репозиторий в архиве с 11.09 [вторично: https://techcrunch.com/2026/09/15/nitter-and-xcancel-are-dead-again-after-xs-latest-legal-actions/; страница по таймауту не открылась, данные из выдачи]. Без входа x.com почти ничего не показывает. Значит, чтение X возможно только из своей авторизованной сессии.
- X API: единственный самообслуживаемый путь — оплата за использование; чтение поста $0,005, пользователя $0,01, чтение своих данных $0,001 (с 20.04.2026) [вторично, блоги-перепечатки, сверять с docs.x.com: https://www.outstand.so/blog/x-api-pricing]. Для личного использования это годится как запасной канал «сохранить свои закладки/лайки», не как основа ленты [гипотеза].

## 4. Незакрытые потребности (с доказательствами)

1. Память растёт в фоне и после долгой работы. Telegram Desktop: 12–13 ГБ в фоне (tdesktop #30870, 06.2026). Instagram: рендерер на Reels/Stories растёт до 19–20 ГБ за 30–45 мин (Brave #57304, 18.07.2026, открыт; воспроизведён в Chrome beta по комментарию, без upstream-бага) [проверено]; на Brave Community 12 ГБ (05.2026) [вторично]. Ferdium: по умолчанию ничего не гибернируется (#2363) [проверено].
2. Незаметно слетающий вход. Ferdium #2567 и #2600 [вторично]; Instaloader: сессия «инвалидирована чекпоинтом» [вторично]; yt-dlp добавил детекцию «умерших» cookies [вторично]. Потребность: явное состояние «служба вышла, нужен вход» и бэкап/восстановление профиля.
3. Нет единого поиска по трём сервисам с локальным индексом: у Beeper поиск не описан в обзорах; в хабах (Ferdium, Rambox, Wavebox) только вкладки с общим бейджем [вторично; отсутствие подтверждено лишь по просмотренным описаниям, не по руководствам] — [гипотеза] ниша свободна.
4. Батч-выгрузка с возобновлением и без бана. tdl закрывает Telegram; для X/Instagram решения без GUI и с 429-проблемами (gallery-dl, Instaloader). Нужна очередь с лимитами, паузами, возобновлением, дедупликацией.
5. Telegram в РФ без VPN: MTProxy деградирует (3 из 27), tg-ws-proxy популярен, но стойкость не измерена. Для встроенного клиента нужны несколько транспортов и самоконтроль (какой работает прямо сейчас).
6. Блокировка аккаунта за «неофициальность». Beeper: условия Meta запрещают, предупреждения «automated behavior» (help-центр, пересказ) [вторично]; Bellingcat про Instaloader [вторично]. Потребность: низкая частота запросов, один постоянный профиль/устройство, без массового опроса.
7. Уведомления. Ferdium: проблема Google Chat бейджа, исправление (2026) [вторично]; Rambox выключает гибернацию для мессенджеров ради уведомлений [вторично]; браузерные уведомления Instagram в фоне ненадёжны [вторично, низкое качество источника]. Компромисс «спать, но будить по событию» не решён ни у кого из просмотренных.
8. Нет «читалки X без аккаунта» после гибели Nitter — для одного пользователя с аккаунтом это не проблема.

## 5. Приёмы экономии памяти и CPU

Подтверждено первичными источниками:

1. Общая среда WebView2. Все WebView2 одного приложения с одинаковыми папкой данных и аргументами запуска делят один browser-процесс; разные папки данных — отдельная группа процессов (browser, GPU, network, utility) [проверено: https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model; рекомендация «одна CoreWebView2Environment на приложение» — https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance, страница обновлена 02.09.2026].
2. Замер на реальном приложении (datrope PR #7, Win debug, 5 серверов, страницы без входа, 2 прогона): процессы 39 → 14, private memory 987 → 446 МБ (−55%), working set 2133 → 733 МБ, idle CPU 114 → 20 мс/с; каждый новый сервер ≈ 45 МБ вместо 151 МБ [проверено: https://github.com/weeklyvillain/datrope/pull/7]. Цена: изоляция только по origin (общие cookie с `Domain=`), общий HTTP-кеш, удаление данных сервиса через CDP `Storage.clearDataForOrigin`, один повторный вход после миграции. Эффект Low-цели в этом замере не выделен.
3. Профили вместо папок. Microsoft: несколько профилей под одной папкой данных делят память, CPU и диск [проверено: process-model и performance]. Для Tauri: wry #1321 «Support for Browser Profiles» (открыт 19.07.2024, закрыт 26.01.2026, вновь открыт 24.07.2026; связанный PR #1738 открыт) [проверено: https://github.com/tauri-apps/wry/issues/1321]. Вывод: [гипотеза] профили на Windows в Tauri пока недоступны штатно; нужен либо прямой вызов WebView2 COM (через `with_webview`), либо форк wry.
4. Сон. `TrySuspend`: доступен с WebView2 1.0.774.44; `IsVisible` должен быть false, иначе `ERROR_INVALID_STATE`; приостанавливает таймеры и анимации, освобождает память рендерера, автоматически возобновляется при показе; best-effort; «условия, мешающие сну» перечислены в Sleeping Tabs FAQ [проверено: https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_3].
5. Низкая цель памяти без остановки скриптов. `MemoryUsageTargetLevel = Low` на неактивных WebView (интерфейс `ICoreWebView2_6`), скрипты и сеть продолжаются, память может уйти в своп; возврат в Normal вручную; не смешивать с `TrySuspend` (сам ставит Low и при `Resume` Normal); `IsVisible=false` не нужен [проверено: https://github.com/MicrosoftEdge/WebView2Feedback/blob/main/specs/MemoryUsageTargetLevel.md; в документе есть опечатки в именах констант]. Для сервисов, которые должны получать уведомления, это единственный разрешённый Microsoft путь [гипотеза по этой логике].
6. Периодически перезагружать долгоживущую страницу, чтобы вернуть процесс к чистому состоянию; не отключать GPU без причины; не создавать лишних WebView2 (перенавигировать один) [проверено: Microsoft performance].
7. Конфликт аргументов: в Tauri смена `additional_browser_args` на одном окне при общей `data_directory` ломает создание вида (HRESULT 0x8007139F) — issue tauri #11144 [вторично]. При общей папке аргументы должны совпадать у всех [проверено: process-model: «second environment fails»].
8. Chromium-флаги: `--renderer-process-limit=1`, `--enable-features=msLowEndDeviceMode,msMemoryCoordinatorPriorityControl`, `--js-flags=--max-old-space-size=64` предлагаются в проектах, но эффект там не измерен (corral-desktop #198, закрыт 21.09.2026 без итоговых цифр); `ProcessPerSiteUpToMainFrameThreshold` в WebView2Feedback #5135/#5321 не уменьшал число рендереров [вторично: выдача]. Официальной подтверждённой рекомендации нет [проверено как отсутствие в документации Microsoft].
9. Рендереры не схлопываются между сайтами: число рендереров зависит от числа разных origin даже при общей папке [проверено: process-model]. Общая среда убирает накладные browser/GPU/utility, но не рендереры трёх сервисов.
10. Electron-аналог (для сравнения, не для вашего стека): `backgroundThrottling` по умолчанию true; с Electron 28 `false` у одного WebContents отключает троттлинг кадров для всего окна; закрытие вида `contents.close()` и пересоздание на том же `persist:`-разделе сохраняет вход (рецепт «сон выгрузкой» выведен из документации, не из готового примера) [вторично/гипотеза]. Wavebox, Ferdium, Rambox реализуют сон на этом принципе или на Chromium-discard.

Практический порядок для Egoist Social [гипотеза, проверять замером]: (a) одна среда и общие аргументы; (b) выгрузка неактивного сервиса — `TrySuspend`, если не нужны уведомления, иначе Low; (c) периодическое пробуждение по таймеру для уведомлений; (d) ограничение кеша медиа Web A; (e) метрика «память по службам» в UI, как у Wavebox.
