### 2.1 FLOOD_WAIT на исследовательском пути

Текущее поведение выяснено по коду: `TelegramClient.invoke` для исследовательских запросов делает `throw e` сразу (строка ~1260) и `downloadFile` для них тоже (`if (isResearchRequest) throw err`), то есть клиент молча не спит. Раньше воркер превращал ошибку в `RATE_LIMITED` с `retryAfterMs`. Теперь событие `error` несёт ещё и точные `seconds` (0–86400) и `waitKind` (`FLOOD_WAIT`, `PREMIUM_FLOOD_WAIT`, `SLOWMODE_WAIT` либо собственные потолки Relay); Rust проверяет поля и отбрасывает неверные.

**Отклонение от формулировки задачи.** Структура получилась не `{code: 'FLOOD_WAIT', seconds}`, а `{code: 'RATE_LIMITED', waitKind: 'FLOOD_WAIT', seconds}`. Код `RATE_LIMITED` оставлен, потому что установленный демон (этап 1) знает только его: незнакомый код он принял бы за «прочий сбой» и повторил бы запрос по экспоненте, не дожидаясь паузы платформы — это и есть ранний повтор, которого нужно избежать. Новый демон принимает оба кода (`FLOOD_WAIT` — синоним на будущее).

Частичный успех. Если ожидание пришло после того, как хотя бы одна страница уже отдана, и демон прислал `partialOnFlood: true`, запуск завершается не ошибкой, а `done {outcome: 'partial', reason: 'FLOOD_WAIT', nextCursor, floodWait: {seconds, waitKind}}`: отданная страница не пропадает, курсор проверенный. Ожидание во время обработки страницы (например, скачивание медиа внутри страницы) остаётся ошибкой: курсор такой страницы ещё не продвинут.

### 2.2 Прямой тракт байтов медиа

Раньше: воркер → base64 кадрами по 48 КиБ → Tauri → Node-помощник → именованный канал → демон → диск (baseline этапа 0: 36–44 МиБ/с на синтетике). Теперь, если Relay объявил `media_spool`, демон просит `mediaSink: 'spool'` и ключ `mediaKey` (32 hex):

1. Воркер шлёт `media_open` с `sink: 'spool'`, отпечатком файла (16 hex) и точкой возобновления.
2. Куски по 1 МиБ идут из воркера в основной поток и из него в Rust **сырым двоичным телом** новой Tauri-командой `relay_research_media_chunk` (заголовки `x-request-id`, `x-nonce`, `x-media-id`, `x-sequence`). JSON, base64, помощник и канал демона не участвуют.
3. Rust (`research_spool.rs`) дописывает файл `<состояние>\spool\<ключ>.<отпечаток>.part`: имя строится только из проверенных hex-значений (ни страница, ни демон не выбирают путь записи), каталог и корень не должны быть ссылками или точками повторной обработки, при остатке диска меньше `размер + 1 ГиБ` запись не начинается (`DISK_RESERVE`), порядок кусков, размер куска (≤ 4 МиБ) и объявленная длина проверяются, SHA-256 считается по мере записи. При возобновлении `.part` обязан существовать с тем же отпечатком и быть не короче точки; хвост отрезается, префикс хэшируется заново.
4. `media_close` уходит демону с `spool: {name, bytes, sha256}` после `sync_all` и переименования `.part` → `.done`.
5. Демон (`media-resume.mjs`) проверяет имя (ключ, `.done`), обычный файл с одной ссылкой, размер и SHA-256 сам, затем переносит файл в каталог задания (rename; на другом томе — копия с `fsync` и повторной проверкой хэша) и записывает проверенный хэш в `media-manifest.json`.
6. Файлы spool старше 14 дней удаляются Rust при следующем открытии.

Новая команда Tauri получила отдельное разрешение `relay-research-media` (`tauri/permissions/research-bridge.toml`) и отдельный файл `tauri/capabilities/research-media-main.json` (`local: true`, только `main`), в `default.json` ничего не добавлялось; `build.rs` и `generate_handler!` дополнены (preflight сверяет их). Добавлена зависимость `sha2 = "0.10.9"` (версия уже была в `Cargo.lock` через `tauri`; в локе добавилась одна строка). Границы размера не менялись: 1 ГиБ на файл, 2 ГиБ на задание.

Резервный путь: без объявления `media_spool` или без `mediaSink` всё идёт прежним base64-путём, байт в байт.

### Дефекты, найденные самими проверками (все исправлены)

1. Запись в возобновлённый файл на стороне демона: при возобновлении `.part` запись через `FileHandle.writeFile` на дескрипторе `r+` писала не в точку возобновления (тест завис на 97 с и упал с `Array buffer allocation failed`); запись стала позиционной (`handle.write(bytes, 0, len, active.size)`) для всех путей.
2. Гонка в планировщике: при `done` с `floodWait` пауза вступала в силу после чекпоинта страницы, и в этот промежуток планировщик успевал отправить следующий шаг в окно паузы (тест видел 1 ранний повтор из 12 источников × 450 записей). ## 6. Ограничения и риски

- **Не проверено в живой среде**: поведение Tauri 2 на двоичном теле команды из WebView2 (передача `Uint8Array` из воркера в основной поток структурным клонированием, регистр имён заголовков, предел размера тела); работа новой команды под capability; скорость тракта; реакция Telegram на 2–3 параллельных запроса; точные формы `FLOOD_WAIT` на `GetFullChannel`/`Search` у пробы; поведение устаревшей установки (старый демон с новым Relay: возможности просто не используются, смешанные версии на живом приложении не проверялись).
- **Параллель повышает риск ожидания для запросов «в полёте»**: пока демон не узнал о `FLOOD_WAIT`, второй шаг может уже лететь и тоже получить ожидание; в модели синтетики такие запросы не штрафуются (пауза считается от момента ответа), в реальности возможна вторая пауза. Демон её учитывает (продлевает паузу, не растит интервал второй раз), но число таких случаев — предмет пилота. Если их много, ставится `policy.limits.telegramParallel = 1` без пересборки.
- **Аварийный потолок в Rust считает старты `run`, а не запросы MTProto** (Rust их не видит); настоящий счёт запросов — 240/мин и 12/мин на разрешение имён в воркере, оба хранятся в памяти и обнуляются перезапуском Relay. Суточный бюджет 500 разрешений тоже обнуляется перезапуском; постоянный суточный бюджет ведёт демон.
- **`probe` стоит 5–6 запросов на источник** (три из них — поиск по одному сообщению для медиа-счётчиков) и тратит бюджет `resolve`; для тысяч источников демон считает не более 12 на платформу и экстраполирует. Счётчики Telegram бывают приблизительными (`inexact`), тогда оценка сохраняет запас.
- **Файл spool лежит на системном диске в `%USERPROFILE%\.egoist-research\spool`** до переноса в выгрузки; при другом томе выгрузок перенос — копия (нужен двойной объём). Предел файла 1 ГиБ не менялся; его повышение — решение владельца.
- **SHA-256 проверяет целостность тракта, а не соответствие Telegram**: Telegram не отдаёт хэш документа, эталон — независимая загрузка. Порча `.part` на диске между запусками без внешнего эталона не обнаруживается (префикс хэшируется заново и считается верным).
- **Время жизни отпечатка**: если сообщение изменилось (другой файл), возобновление даёт `RESUME_MISMATCH`, и демон один раз перекачивает с нуля.
- **Комментарии, темы, похожие каналы, предпросмотр инвайта** реализованы в Relay и объявлены, но стадий оркестратора под них в демоне нет (доступны на уровне операций моста); `join_chat` не менялся и остаётся закрыт политикой.
- **Тест Rust изменён по смыслу**: `cancelled_run_remains_busy_until_owned_terminal_settlement` проверяет теперь занятость при трёх отменённых запусках (раньше при одном); остальные 125 прежних тестов не менялись.
- Изменённый `bridge-server.mjs` входит в манифест runtime (размер и SHA-256 обновлены, preflight проходит); при пересборке манифест надо пересчитать, если файл правится ещё раз.
- Версия Relay и `CHANGELOG` не менялись: релиз, `npm run version:sync` и коммиты — за координатором. `tauri/gen/schemas/*` пересобрались при компиляции и содержат только добавленное разрешение.
