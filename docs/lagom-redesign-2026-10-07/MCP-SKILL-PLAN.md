## 0. Сводка

**Что есть.** Egoist Social MCP уже решает самое трудное и самое рискованное: безопасный мост к аккаунтам Relay (именованный канал, HMAC в обе стороны, проверка PID/времени запуска/EXE, привязка задания к аккаунту и эпохе), долговечные задания на диске, чекпоинты, курсоры, отмену, запись медиа с SHA256, локальный FTS-индекс. 169 тестов-фикстур [проверено: сумма `test(` по `SMCP\src\research\*.test.mjs`]. Это основа, а не черновик; дублировать её не нужно.

**Чего нет для цели «тысячи источников, миллионы сообщений, файлы, без загвоздок».** Система спроектирована как «одно задание ≤ 1000 записей и ≤ 300 секунд, по одному заданию на платформу, всё остальное — вручную через агента». Для масштаба нужен слой оркестрации над этими заданиями: списки источников, план с оценкой, планировщик с учётом лимитов аккаунта, автоматическое возобновление после FLOOD_WAIT и сбоев, нормализованное хранилище с дедупликацией, выборка с пагинацией, прогресс, экспорт файлом. Сегодня всё это ложится на агента и контекст.

**Три находки, которые стоит исправить первыми.**

1. **MCP и демон не стартуют на этом ПК без файла, которого нет.** `readResearchConfig` безусловно читает `~\.codex\brain-pointer.json` (`SMCP\src\research\config.mjs:25`); в `~\.codex\` такого файла нет [проверено: листинг имён, содержимое не читалось], а репозиторий правил как раз убрал связку с brain-pointer (коммит `8c6ac05`). Ошибка не перехватывается. Исправление — одна строка (значение по умолчанию для workspace).
2. **Нет «списка заданий» и «ожидания».** Демон принимает только `capabilities, status, submit, submit_join, get, cancel, shutdown` (`SMCP\src\research\ipc.mjs:5`). После потери контекста агент не может найти свои задания; следить за ходом можно только опросом `social_job`.
3. **FLOOD_WAIT убивает задание.** Для исследовательских запросов GramJS не ждёт и не повторяет, а сразу бросает ошибку (`RELAY\src\lib\gramjs\client\TelegramClient.ts:1258-1262`), брокер переводит задание в `rate_limited` без автоповтора (`SMCP\src\research\broker.mjs:22`, `:469`). Для массового парсинга нужна обратная логика: ожидание ровно `seconds` и продолжение с того же курсора.

**Предлагаемая архитектура (кратко).** Ядро остаётся двухслойным, как сейчас, но разделение обязанностей уточняется: Relay (Rust + GramJS-воркер + скрытые WebView) выполняет **один шаг** под аккаунтом (страница истории, чтение поста, фрагмент медиа) и держит жёсткие аварийные потолки; внешний Node-демон (уже существует) становится **оркестратором**: источники → план → задание → задачи → результаты → экспорт, SQLite как рабочее хранилище, JSONL как проверяемый сырой архив, планировщик с квотами на аккаунт и адаптивным троттлингом. MCP остаётся тонким адаптером: 9 инструментов вместо 8 «смешанных», плоские схемы вместо схемы на 19 ветвей (сейчас `social_submit` — 18 КБ из 23,5 КБ всего каталога [проверено: замер]).

**Skill.** Один skill `egoist-social-research` с тремя ветками-справочниками (`references/telegram.md`, `x.md`, `instagram.md`), а не три отдельных skill: так велят правила (близкие описания ухудшают выбор, одно правило — одно место, ветвление решается раскрытием по требованию). Три варианта владельца реализуются как три справочника + общий каркас; если проверка триггеров покажет путаницу, три тонких входа можно сгенерировать из одного шаблона скриптом.

**Честные пределы.** Telegram (MTProto, штатный клиент): десятки-сотни тысяч сообщений в час на аккаунт при аккуратном темпе; миллионы — это часы-сутки очереди, не минуты. X и Instagram (скрытый WebView, чтение DOM): сотни-тысячи записей в час, с высоким риском ограничений и нарушением условий платформ; «миллионы» там нереалистичны. Все числа — гипотезы до пилота (этап 0/2). Риск блокировки аккаунтов и нарушения ToS — реальный; см. раздел 3.13 и вопросы 2, 9.

**Про слово «Asynth».** Основная трактовка — «async»: асинхронный массовый парсинг (вопрос 1).

### 2.2 Связь с Relay

Контракт — `SMCP\BRIDGE-CONTRACT.md`.

**Терминология.** В `RELAY\AGENTS.md` (раздел «Границы безопасности Tauri», последняя строка) сказано «Relay Control API по именованному каналу». Проекта `Egoist Relay Control MCP`, упомянутого в `RELAY\docs\AUDIT-1.1.0.md:60`, в `Инфраструктура\` нет [проверено: листинг]. Рекомендация: переименовать в документах «Relay Control API» → «Relay account bridge», чтобы агент не искал второй интерфейс.

Протокол моста [проверено, `BRIDGE-CONTRACT.md:13-28`]:

- Транспорт: UTF-8 JSON-строки, кадр ≤ 262144 Б; сообщения `status | capabilities | run | cancel`; взаимная HMAC-проверка (клиент проверяет сервер до отправки запроса; MAC запроса включает nonce сервера и runtimeId).

- Ограничения Rust: ≤ 16 одновременных запросов (`research_bridge.rs:388`), **один `run` на провайдера** (`PROVIDER_BUSY`, `:397`), запрет ключей `script/eval/method/headers/cookies/session/authKey/accessHash/path/outputDirectory` во входе (`:156-185`), вход ≤ 64 КиБ.

Брокер на каждое задание опрашивает готовность (`broker.mjs:341-361, 417`) и при отправке — ещё раз (`:538`). [гипотеза] на задание уходит несколько секунд только на служебные вызовы; для тысяч заданий это часы и тысячи процессов PowerShell.

### 2.3 Модель заданий

Состояния: `queued, running, rate_limited, auth_required, completed, partial, failed, cancelled, interrupted` (`broker.mjs:7`). Хранение: один JSON на задание в `~\.egoist-research\jobs\<uuid>.json`, ≤ 128 КиБ, атомарная запись с fsync (`job-store.mjs:187-218`), блокировка одного брокера (`:135-166`). История ≤ 10000 заданий, ≤ 64 в очереди/работе на провайдера (`broker.mjs:51-52`), все задания держатся в памяти (`:299`).

Очередь: FIFO на провайдера, одно задание за раз, три провайдера параллельно (`broker.mjs:480-494`).

Идемпотентность: `idempotencyKey` → SHA256 → отображение в память и на диск; повтор того же нормализованного запроса возвращает то же задание, другой запрос с тем же ключом — `IDEMPOTENCY_CONFLICT` (`broker.mjs:526-530`) [проверено, хорошо].

Восстановление: при старте все `queued/running` переводятся в `interrupted` с `PROCESS_INTERRUPTED`; **автоматического возобновления нет**, нужен новый submit с курсором (`broker.mjs:327-329`, комментарий: «Input and auth values are deliberately not persisted»). [наблюдение] Для операций чтения повтор безопасен; осторожность оправдана только для `join_chat`. Сегодня из-за этого любая перезагрузка демона теряет всю очередь.

Нет: списка заданий, приоритетов, пауз, повтора отдельных упавших источников, зависимостей между заданиями, прогресса в процентах, событий [проверено: `ipc.mjs:5`, `broker.mjs` публичный интерфейс `status/submit/get/cancel/close`].

### 2.6 Медиа

Путь байтов: renderer-воркер скачивает кусками по 1 МиБ **последовательно** (`research.ts:99, 599-617`), режет на кадры по 48 КиБ, base64 (+33%), через Tauri → скрытый Node-помощник → именованный канал → демон → диск (`research_bridge.rs:963+`, `bridge-provider.mjs:192-203`). Возобновления с середины файла нет: после сбоя остаётся `.part` и запись в partial-manifest, но следующий submit скачивает заново [наблюдение: код возобновления не найден]. Защищённый контент (`noforwards`) корректно пропускается с `MEDIA_RESTRICTED` (`research.ts:553-557`) [проверено, правильное решение, сохранить]. Видео X/Instagram в формате blob/HLS/DRM не поддерживаются (`README.md:26`, coverage `:24`).

[гипотеза] Пропускная способность этого пути на порядок ниже сети: три пересериализации и base64 на каждый 48-КиБ кадр. Реальная цифра неизвестна — замерить на этапе 0 (синтетический источник), потом на пилоте.

### 2.7 FLOOD_WAIT и ограничения платформ

- Telegram: ошибки `FLOOD|RATE_LIMIT` → код `RATE_LIMITED` с `retryAfterMs = seconds*1000` (`research.ts:1107-1129`) — **информация сохраняется**. Для платного поиска постов есть предварительная проверка квоты `CheckSearchPostsFlood` (`research.ts:471-480`). Автоматического ожидания нет ни на стороне GramJS (research-запросы не спят, `TelegramClient.ts:1258-1262`), ни у брокера: задание завершается `rate_limited`, `retryAfterMs` кладётся в ошибку (`broker.mjs:277, 469`).
- Нет учёта «бюджета» аккаунта: частоты запросов, суточных счётчиков `resolveUsername`/поиска/скачиваний. Нет разграничения нагрузки UI и исследований на одном клиенте (это один и тот же GramJS-клиент).
- Каждое задание заново выполняет `contacts.resolveUsername` для канала (`research.ts:790-795`); числовой ID берётся из кэша `localDb` только внутри сеанса renderer (`:768-771`). Для истории из 1000 срезов это 1000 разрешений имени — известный источник FLOOD_WAIT [гипотеза по поведению API; в коде кэша между заданиями нет].
- X/Instagram: прокрутка корневого скроллера и пауза фиксированные 700 мс (`social-read.js:590-595`); окно ожидания DOM 15 с, опрос 150 мс (`:12-13`). Вызовы платформы не перехватываются, читается отрисованный DOM. Ошибки лимита платформы представлены как `CHALLENGE_REQUIRED` / `RATE_LIMITED` / `AUTH_REQUIRED` (`social-read.js:93-111`).
- Telegram, выборка по дате: запрос всегда начинается с новейших сообщений (`offsetDate: 0`, `research.ts:391`), фильтр `after/before` применяется к уже полученным; при `SCAN_LIMIT` в 1000 просмотренных сообщений глубокий диапазон достигается только цепочкой курсорных заданий. Параметр `offset_date` протокола не используется [проверено].
- Инкрементальный режим «только новое с прошлого раза» (`min_id`) не реализован: `minId: 0` (`research.ts:391-392`).

### 2.8 Прогресс, отмена, возобновление

- Прогресс во время работы: чекпоинты пишутся на диск и обновляют `count/files/nextCursor` задания (`broker.mjs:435-445`), но снаружи виден только `social_job` по запросу. Событий, процента, оценки времени, числа источников нет.
- Отмена: `cancel` прерывает активное задание; принятые данные сохраняются (`broker.mjs:578-591`); есть `completionUncertain`. Хорошо.
- Возобновление: через `cursor`, привязанный к провайдеру, источнику, эпохе аккаунта; чужой/старый курсор отвергается `CURSOR_SOURCE_MISMATCH`, `STALE_ACCOUNT` (`broker.mjs:31-33`). Корректно, но вручную.

[проверено, сильные стороны]:

## 3. Целевая архитектура

### 3.1 Разделение обязанностей

Принцип: **шаг под аккаунтом — в Relay; смысл, очередь и данные — в демоне; MCP — тонкий адаптер.** Планировщик не переносим в Rust: логика меняется часто, её удобно тестировать на 169 существующих и новых Node-тестах, и она не должна требовать пересборки установщика Relay на каждое изменение. Rust оставляет за собой только то, что обязано быть жёстким (аварийные потолки).

└──▼───────────────────────────────────────────────┘
   │ именованный канал демона (HMAC), + события

**Альтернатива «встроить демон в Relay» (вариант B)**: один процесс владеет мостом и заданиями, пропадают двойной канал и HMAC-рукопожатие. Минусы: каждое изменение планировщика — релиз установщика; демон не живёт без Relay (сейчас живёт и умеет его запускать); тесты придётся переносить. Рекомендация: этапы 1–3 на варианте A (внешний демон), оценить B после стабилизации контракта (вопрос 8). Контракт демона из раздела 3.2 переносим без изменений.

### 3.2 Единый контракт: источники → план → задание → результаты → экспорт

**Термины** (один термин на понятие): *источник* (source) — канал/группа/профиль/тег/пост; *план* (plan) — проверенный и оценённый набор источников с целью; *задание* (job) — запущенный план; *задача* (task) — внутренняя единица (источник × стадия × диапазон), агенту не нужна; *запись* (item) — сообщение/пост/профиль/комментарий; *экспорт* (export) — файл для внешней обработки.

1. **Источники.** Три способа: список в аргументах (≤ 200), файл `.txt/.csv/.jsonl` в рабочей папке (≤ 50 000 строк; демон сам читает, нормализует, удаляет дубликаты, помечает невалидные), сохранённый список. Агент не передаёт тысячи ссылок через контекст.
2. **План (`social_plan`).** Разрешает источники, считает дубликаты и недопустимые, при `probe=true` делает дешёвые запросы счётчиков (для Telegram: размер истории через `GetHistory(limit=1)`, `participants_count`, подписчики; для X/IG — счётчики на странице профиля), оценивает записи, байты медиа (по выборке), время при текущем состоянии регулятора, расход бюджета аккаунта, риск. Возвращает `planId` и `confirmationRequired` (порог — в `policy.json`). Проба тоже тратит бюджет аккаунта — это видно в ответе.
3. **Задание (`social_run`).** Принимает `planId`, идемпотентен по `idempotencyKey`. Создаёт задачи по источникам, ставит в очередь, отвечает сразу (< 1 с).
4. **Ход (`social_job`).** Сводка/источники/события/ошибки; **long-poll** до 50 с до изменения (`wait`); события имеют монотонный `seq`.
5. **Управление (`social_job_control`).** `pause | resume | cancel | retry_failed`. Отмена сохраняет принятые данные.
6. **Результаты (`social_records`, `social_stats`).** Выборка из накопленного хранилища с фильтрами, FTS, пагинацией по ключу, бюджетом байт; агрегаты.
7. **Экспорт (`social_export`).** Файл CSV/JSONL/Markdown/HTML (позже Parquet) в рабочей папке + SHA256; тяжёлые данные идут файлом, а не через контекст.

**Состояния задания.** `planned → queued → running ⇄ waiting → completed | completed_with_gaps | failed | cancelled`, плюс `paused`. `waiting` всегда с причиной и временем: `rate_limit(until)`, `bridge_unavailable`, `account_unavailable`, `disk_low`, `challenge_required`, `awaiting_owner`. `completed_with_gaps` — есть пробелы (закрытые источники, ограничения платформы), перечисленные поимённо; `completed` без пробелов не выдаётся, если не подтверждён пустой/полный источник (правило проекта: «unavailable/challenge/denied ≠ пусто», `SMCP\AGENTS.md:7`).

**Состояния источника.** `pending | running | waiting | done | partial(gap) | denied | unavailable | failed | skipped`.

**Единый конверт ответа** (все инструменты):

```json
{ "ok": true,
  "data": { },
  "page": { "returned": 25, "hasMore": true, "nextCursor": "…", "truncatedByBytes": false },
  "evidence": [ { "locator": { "jobId": "…", "segment": "…", "offset": 0, "length": 0 } } ],
  "notes": [ "…" ] }
```

и при ошибке (`isError: true`):

```json
{ "ok": false,
  "error": { "code": "RATE_LIMITED", "message": "…",
             "recovery": "Задание перешло в waiting до 2026-10-07T21:40Z; повторять не нужно.",
             "retryable": true, "retryAfterMs": 31000, "completionUncertain": false } }
```

Коды отказа делятся на «пусто» (`data.items=[]` + `emptyReason: confirmed_empty | not_collected | filtered_out`), «нет доступа» (`ACCESS_DENIED`), «данные недоступны» (`UNAVAILABLE`, `UNSUPPORTED`, `CHALLENGE_REQUIRED`), «лимит» (`RATE_LIMITED` — для задания это состояние `waiting`, а не ошибка), «сбой» (`ADAPTER_FAILED`, `STALE_ACCOUNT`). Тексты `recovery` — по таблице `ERRORS` из `broker.mjs:15-50`, без сырых ошибок платформы.

### 3.3 Очередь, квоты на аккаунт, адаптивный троттлинг

**Регулятор темпа аккаунта (демон).** На каждый `accountRef` и класс запросов — своё ведро токенов с AIMD (аддитивное увеличение, мультипликативное уменьшение):

| Класс | Примеры Telegram | Начальный темп* | Суточный мягкий бюджет* |
|---|---|---|---|
| `resolve` | `contacts.resolveUsername`, `checkChatInvite` | 1 запрос / 3 с | настраиваемый, по умолчанию 200 |
| `history` | `messages.getHistory`, `getReplies`, `search` | 1 запрос / с (1→3 параллельно) | без жёсткого, наблюдать FLOOD |
| `search` | `contacts.search`, `channels.searchPosts` | 1 запрос / 5 с | 100 |
| `members` | `channels.getParticipants` | выключено по умолчанию | 0 |
| `media` | `upload.getFile` | 1 поток | дисковый бюджет |
| `join` | `channels.joinChannel` | вручную | 0 (политика) |

\* [гипотеза] стартовые значения консервативные, откалибровать на пилоте этапа 2; живут в `policy.json`, не в коде.

Правила:

1. **FLOOD_WAIT N с**: класс аккаунта уходит в `cooldown` на `N × 1,1 + jitter`; темп класса ×0,5; задачи этого класса переходят в `waiting(until)`; планировщик берёт задачи других источников/классов или другого аккаунта. Время сохраняется в БД, перезапуск демона его соблюдает.
2. **Рост** темпа: +10% после 10 минут без ошибок, не выше потолка из `policy.json`.
3. **Длинные ожидания** (N > 900 с): задача паркуется, в событиях `flood_wait_long`; агент видит `waiting` и ETA, не опрашивает.
4. **Размыкатель**: ≥ 3 FLOOD_WAIT за час или `PEER_FLOOD`/`USER_*`/`AUTH_*` → класс `open` на 1 час или до решения владельца; задание → `awaiting_owner`.
5. **Нагрузка UI**: исследования получают не более 50% консервативного бюджета, пока основное окно активно (один и тот же клиент GramJS обслуживает интерфейс); в headless — полный бюджет.
6. **Приоритеты и справедливость**: очередь задач — по `(priority, lastServedAt)`; один большой источник не блокирует мелкие (стадии нарезаются на срезы ≤ 100 записей или ≤ 20 с).
7. **Параллелизм**: Telegram — до 3 шагов под аккаунтом (если регулятор допускает), X/IG — строго 1 на WebView. Аварийный потолок в Rust (например, ≤ 120 запросов/мин на аккаунт) не зависит от демона [гипотеза по значению].
8. **X/Instagram**: «темп» — это пауза между прокрутками и суточный бюджет прокруток/страниц; пауза с джиттером (1–4 с вместо фиксированных 700 мс — `social-read.js:595`) — это вежливость к серверу, а не маскировка; при баннере лимита или проверке — немедленная остановка источника и `waiting: challenge_required`/`rate_limit`, решает владелец. Никакой подмены отпечатка, прокси-ротации или обхода проверок.

**Несколько аккаунтов.** Сегодня мост показывает один `accountRef` на провайдера (`bridge-provider.mjs:34-43`) [проверено]. Мультиаккаунтность (пул) — отдельное решение: она технически возможна, но распределение одного источника между аккаунтами ради обхода лимитов — риск ToS (вопрос 2). Этап 1 закладывает `accountRef` в схему, но использует один.

### 3.4 Возобновление, идемпотентность, дедупликация

- **Атомарный чекпоинт**: страница записей, обновление курсора и счётчики задачи фиксируются одной транзакцией SQLite (WAL). После `kill -9` повторно запрашивается не более одной страницы; дубликатов нет благодаря `UNIQUE(provider, source_id, item_id)`.
- **Задачи чтения автоматически возобновляются** при перезапуске демона и после `waiting`. Исключение — `join_chat`: неопределённый исход читается обратно (членство), затем решает владелец (как сейчас, `BRIDGE-CONTRACT.md:42`).
- **Эпоха аккаунта**: курсор остаётся привязанным к `{accountRef, accountEpoch}`; при смене эпохи задачи, привязанные к закрытым источникам, переходят в `blocked_account`; публичные источники можно продолжить после подтверждения совместимости курсора.
- **Идемпотентность**: `idempotencyKey` на задание (как сейчас); на задачу — `(sourceId, stage, cursorHash)`; на медиа — `sha256` + Telegram `file_unique_id`/URL.
- **Дедупликация**: записи по `(provider, source_id, item_id)`; пересылки и репосты связываются полем `original_ref`, а не сливаются; медиа — по `sha256` (одно физическое хранение, много ссылок); близкие дубликаты текста — столбец `text_fingerprint` (нормализованный хэш), без автоматического удаления.
- **Режимы**: `new` (с нуля), `refresh` (Telegram `min_id`, X/IG — до первого известного ID), `resume_all` (дотянуть незавершённые).

### 3.5 Хранилище: что и почему

| Критерий | SQLite (WAL) | Parquet | JSONL |
|---|---|---|---|
| Транзакционное возобновление (запись + курсор атомарно) | да | нет (неизменяемые файлы) | нет |
| Дедуп `UNIQUE` | да | нет | нет |
| Чтение во время записи | да (WAL) | да, но по файлам | да |
| Поиск FTS5 (в том числе русский) | да, встроен | нет | нет |
| Зависимости при `AGENTS.md`: «только встроенные модули» | `node:sqlite` уже используется (`local-index.mjs:5`) [проверено] | нужен писатель Parquet — зависимость | встроено |
| Человеческая проверяемость, хэш, переносимость | средняя | низкая | высокая |
| Аналитика во внешних инструментах | через экспорт | отлично | средне |

**Решение.**

1. **SQLite — рабочее хранилище**: состояние (источники, задания, задачи, события), нормализованные записи, FTS, медиа-метаданные. **По одному файлу на провайдера** (`telegram.db`, `x.db`, `instagram.db`) плюс `state.db` для заданий: три независимых писателя совпадают с тремя независимыми очередями; сквозной поиск — через `ATTACH` (3 файла укладываются в лимит). Размер: оценка 1 млн сообщений ≈ 0,5–1,5 ГБ с FTS [гипотеза], потолок файла поднимается с 2 ГиБ до настраиваемого (например, 64 ГиБ); сегментирование по году — в запасе.
2. **JSONL — сырой проверяемый архив**: `raw/<provider>/<source>/<seg-0001>.jsonl`, ротация по 64 МиБ, `sha256` в манифесте сегмента; запись SQLite хранит `(segment, byte_offset, byte_length)` — ровно та схема локатора, которая уже есть в индексе (`local-index.mjs:23`). Это сохраняет принцип «`records.jsonl` авторитетен» и проверку хэшей из существующего контракта.
3. **Parquet — только производный экспорт** (этап 5) через уже существующий в репозитории правил skill `polars` из `skills-optional`, без зависимости в проекте.
4. Старые папки заданий остаются читаемыми: импорт в хранилище — отдельная операция «импорт задания» (идемпотентно по `(provider, source, item_id)`), без изменения исходных файлов.

Схема (набросок; поля нормализованной записи — в 4.3):

```sql
sources(source_id PK, provider, ref, canonical_id, kind, label, status, last_checked, meta_json)
jobs(job_id PK, plan_id, state, state_reason, priority, created_at, finished_at, goal_json)
tasks(task_id PK, job_id, source_id, stage, cursor, state, attempts, waiting_until, lease_until,
      account_ref, account_epoch, counts_json)
items(pk INTEGER PK, provider, source_id, item_id, ts, author_id, type, text, lang,
      metrics_json, reply_to, thread_id, original_ref, seg, off, len, content_sha, text_fp,
      UNIQUE(provider, source_id, item_id))
items_fts(text)  -- FTS5, content='items'
media(media_id PK, item_pk, kind, mime, declared_bytes, sha256, path, state, done_bytes)
events(seq INTEGER PK AUTOINCREMENT, ts, job_id, source_id, kind, data_json)
```

### 3.6 Поиск по выгрузкам, в том числе русский

Текущая основа — FTS5 `unicode61 remove_diacritics 2` [проверено]. Слабые места: нет морфологии («канал/каналов/каналами» — разные токены); поведение `ё/е` не закреплено тестом.

Решение по ступеням, всё без внешних зависимостей:

1. **Этап 1**: `unicode61` + префиксный поиск (`слов*`) + тест, закрепляющий `ё=е`, регистр, слова с дефисом, эмодзи, ссылки/хэштеги (`#` и `@` как часть токена через `tokenchars`).
2. **Этап 3**: столбец `text_stem` — собственный компактный стеммер русского (алгоритм Snowball, ≈ 150 строк JS, без пакета) и английский (Porter); запрос нормализуется тем же стеммером; режим `lang: "ru" | "en" | "auto"` (определение языка по доле кириллицы). Эффект на полноту проверить на размеченной выборке (критерий — раздел 5).
3. **По запросу**: триграммный FTS (`tokenize='trigram'`) для подстрок и опечаток по выбранным источникам; индекс в 2–3 раза больше [гипотеза], поэтому не по умолчанию. Доступность `trigram` в версии SQLite, встроенной в Node 24, проверить [не проверено].
4. Результат поиска — как сейчас: источник, сниппет, локатор `(segment, offset, length)`, хэши; плюс `corpus.incomplete` и список пробелов — «нет совпадений» относится только к собранному.

Запрос остаётся «литеральными терминами и фразами в кавычках, без SQL/FTS-операторов» (как `mcp.mjs:54`) — это защищает от инъекций в MATCH и сохраняется.

### 3.7 Крупные медиа

1. **Метаданные всегда** (тип, размер, длительность, `file_unique_id`, миниатюра по политике); **байты — по политике** (`none | thumbnails | up_to_size | all`, `maxFileMiB`, `maxTotalGiB`). План показывает оценку объёма до запуска; свыше порога — `confirmationRequired`.
2. **Отдельная полоса медиа** с собственным темпом и дисковым бюджетом; не блокирует текстовые задачи.
3. **Контентно-адресуемое хранилище** `media/ab/cd/<sha256>.<ext>`; записи ссылаются на `media_id`; повторное вложение не скачивается второй раз.
4. **Возобновление**: `.part` + `done_bytes`; Telegram — продолжение с offset (протокол поддерживает диапазоны, код уже передаёт `start/end`, `research.ts:608-611`).
5. **Тракт данных** (этап 2, требует релиза Relay): сейчас байты идут base64 через три прыжка. Предлагается команда Tauri «записать фрагмент в путь, выделенный демоном внутри корня выгрузок» (путь выдаёт демон, Rust проверяет префикс и отсутствие ссылок, воркер пишет двоичные фрагменты без base64). До замеров не обещать выигрыш; на этапе 0 снять базовую скорость текущего пути на синтетике.
6. **Видео X/IG (blob/HLS)**: в `RELAY\runtime\` уже лежит `yt-dlp.exe` [проверено: листинг]. Для **публичных** постов без cookie он потенциально закрывает пробел, но поддержка зависит от платформы и меняется; использование cookie запрещено принципами проекта. Решение — вопрос 9.
7. Защищённый контент (`noforwards`) не скачивается (как сейчас) — сохранить.
8. Транскрибация (`transcribe`) остаётся стадией обогащения над скачанным медиа; лимиты по минутам — в плане.

### 3.8 Прогресс-события

- Журнал `events(seq, ts, kind, …)` в БД: `job_state, source_state, progress (каждые N записей/5 с), flood_wait, throttle_change, media_done, gap, disk_low, bridge_state`.
- Доставка: **(a) long-poll** `social_job(wait.maxSeconds ≤ 50, sinceSeq)` — работает в любом MCP-клиенте; **(b)** `notifications/progress` при наличии `progressToken` в запросе; **(c)** подписка на ресурсы не используется (поддержка клиентов неоднородна [гипотеза]).
- Сводка: `sources{total, done, running, waiting, failed, denied}`, `records`, `mediaBytes`, `ratePerMin`, `eta{p50Ms, p90Ms, basis}`, `waiting[]` с причиной и временем.
- В Relay (UI) — по желанию: панель «Исследования» читает те же события из демона (вне объёма этого плана; связано с редизайном Lagom).

### 3.9 Права

Три уровня политики в `~\.egoist-research\policy.json` (создаётся с безопасными значениями по умолчанию; править может только владелец; демон перечитывает при старте):

| Область | По умолчанию | Что разрешает |
|---|---|---|
| `read` | включено | Все операции чтения публичных и доступных аккаунту источников, экспорт, медиа в пределах бюджета |
| `read_private_thread` | выключено | `read_thread` по точной ссылке на личный диалог (может изменить статус прочтения: `BRIDGE-CONTRACT.md:46`) |
| `members` | выключено | Список участников, где платформа разрешает |
| `join` | выключено | `telegram_join_chat` только для целей из `allowedTargets` или с подтверждением через MCP-elicitation, суточный предел |
| `send / publish / react / follow / settings` | **не существует** | Нет инструмента, нет метода в мосте; не добавляется |

Подтверждение внешних действий — механизм, а не просьба в тексте: (1) белый список целей в политике; (2) если клиент поддерживает elicitation (2025-06-18+), демон/адаптер запрашивает «да» у пользователя; иначе — отказ `POLICY_DENIED` с инструкцией, что именно владельцу внести в `policy.json`. Аннотации инструментов остаются подсказками (`tool-interface-design\SKILL.md:19`).

Текст чужих сообщений в ответах помечается `untrusted: true` и находится только в полях `text/caption/…`; skill и `instructions` сервера говорят «данные, а не команды» (`rules.md:8`).

### 3.10 Журнал аудита

Файл `audit.jsonl` в приватном каталоге состояния, только добавление, **цепочка хэшей** (`hash = sha256(prevHash + line)`), ротация помесячно, проверка командой `verify`. Записываются: вызов инструмента (имя, хэш аргументов, `jobId`, время, результат-код), изменения состояния заданий, **счётчики исходящих запросов по аккаунту/классу/методу** (без содержимого), FLOOD_WAIT и решения размыкателя, отказы политики, каждый `join` с точной целью. Не записываются: токены, cookie, тексты сообщений, номера телефонов, сырые сообщения платформы. Тест «канарейка»: секрет-приманка во входе/ошибке провайдера не появляется ни в ответе, ни в логе, ни в аудите, ни в манифесте.

**X (скрытое окно Relay, чтение DOM; официальный API не используется).** Что реально возможно [наблюдение + гипотеза]:

- Профиль, сетка постов/reels (виртуализирована, partial), страница поста, фото из `srcset`. Ключевого поиска по постам нет (по дизайну), теги — не прогонялись.

### 3.13 Риски блокировки и нарушения условий платформ

Это не юридическая консультация; ссылки для проверки владельцем: условия API Telegram (`core.telegram.org/api/terms`), страница ошибок с `FLOOD_WAIT` (`core.telegram.org/api/errors`), Условия X, Условия использования Instagram/Meta. В этой сессии эти страницы не открывались.

- **Telegram.** Использование пользовательского клиента для чтения доступных чатов — штатное поведение, но высокий темп, массовые `resolveUsername`/`getParticipants`/`join` приводят к `FLOOD_WAIT` и ограничениям аккаунта; `PEER_FLOOD` и массовые вступления — путь к ограничению или бану [гипотеза по опыту, документирован сам механизм `FLOOD_WAIT`]. Меры: серверные `seconds` соблюдаются буквально; бюджеты; никаких автоматических вступлений; участники выключены.
- **X.** Парсинг интерфейса под сеансом пользователя — не вызов официального API. Возможны: временное ограничение чтения, блокировка за «необычную активность», блокировка аккаунта. Нарушение условий X возможно независимо от технического успеха [из памяти].
- **Instagram.** Самая агрессивная защита: проверки безопасности, ограничения действий, блокировка. Автоматизированный сбор запрещён условиями Meta без разрешения [из памяти]. Консервативные бюджеты, ручное решение владельца при проверке.
- **Общие меры**: исследовательские аккаунты отдельно от основных (вопрос 2); никакого обхода CAPTCHA/проверок/лимитов, подмены отпечатка, ротации прокси; остановка источника при первом признаке ограничения; журнал аудита показывает, что именно ушло с аккаунта.
- **Персональные данные.** Посты и сообщения людей — персональные данные; цели и срок хранения определяет владелец (вопрос 10). Граница с `osint-research`: тот skill — публичные источники и организации, не частные лица (`RULES\docs\skill-routing.md`, строка «Публичные источники, соцсети»); Social MCP — выгрузка из конкретных каналов/профилей через аккаунт, без «досье на человека».

### 4.2 Каталог инструментов MCP

Принципы: плоские схемы без `oneOf` на верхнем уровне (проверка допустимости комбинаций — на сервере, перечень допустимых комбинаций возвращает `social_status`); описания по формуле T1; все ответы с `outputSchema`; префикс `social_` и имя сервера `egoist_social` сохраняются ради совместимости; термин «job» вместо «run».

|---|---|---|---|
