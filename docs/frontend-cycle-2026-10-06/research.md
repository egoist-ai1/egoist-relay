Исходная версия цикла: локальный кандидат 1.5.0, ветка codex/relay-media-operations. Это исходное исследование перед выбором. **Главный вывод.** Для Relay уместна собственная спокойная рабочая оболочка вокруг разных сервисов: понятная карта Telegram/X/Instagram, видимые операции и короткая обратная связь. Декоративная обработка поверхности сервиса может ухудшить ввод и композицию окна.

Обзор не устанавливает качество живых аккаунтов, native DPI/GPU или сетевого транспорта Relay.

**Ferdium: полезный технический урок.** В релизе 7.2.3 перечислены исправления переключения сервисов и округлённых WebView. PR #2544 описывает сильные задержки ввода, особенно при отключённом аппаратном ускорении, после применения clipping к Electron WebView. В прочитанном `src/styles/services.scss` тега v7.2.3 отдельная поверхность сервиса не обрезается ради закругления: имитация углов рисуется псевдоэлементами host. Это подтверждает механизм исправления в Ferdium; перенос величины задержки на Tauri/WebView2 был бы гипотезой. Для Relay вывод — прототипировать эффекты на native-поверхности отдельно и измерять их. [Релиз](https://github.com/ferdium/ferdium-app/releases/tag/v7.2.3), [PR #2544](https://github.com/ferdium/ferdium-app/pull/2544), [проверенный код services.scss](https://github.com/ferdium/ferdium-app/blob/v7.2.3/src/styles/services.scss).

В `Sidebar.tsx` подтверждены горизонтальная/вертикальная раскладка, передача подписей сервисов и badges в Tabbar, отдельные глобальные инструменты. При трёх фиксированных сервисах Relay полезны устойчивое размещение и ясная активность. Каталоги сервисов, workspaces, split-view и множество вариантов настройки не обоснованы текущим сценарием. [Sidebar.tsx](https://github.com/ferdium/ferdium-app/blob/v7.2.3/src/components/layout/Sidebar.tsx).

Автор явно различает подсчёт работы с mocked browser API и замер packaged GUI. В Relay разумно сохранить семантические CSS-переменные и не перестраивать дизайн-систему при каждом переключении; реальное ускорение проверяется отдельно. Статус страницы PR в веб-кэше противоречит включению в релиз, поэтому уверенный вывод о полном кодовом составе делается по тегу, а не по cached status. [PR #2531](https://github.com/ferdium/ferdium-app/pull/2531).

**Telegram: путь к устойчивому результату.** Официальный менеджер загрузок объединяет текущие и недавно полученные файлы, имеет постоянный вход и возврат к чату. Для Relay сильный принцип уже реализован в 1.5.0: панель должна выглядеть частью рабочего процесса, а не архивом технических сообщений. На первой строке нужен понятный результат («Сохранено», «Отправлено», «Прервано», «Исход неизвестен»), ниже источник/файл и объяснение доступного действия. Новое оформление не меняет реальные пределы размера, подтверждения или ограничения восстановления. [Официальный RU-материал](https://telegram.org/blog/downloads-attachments-streaming/ru), [EN-материал](https://telegram.org/blog/downloads-attachments-streaming?setln=en).

**VS Code: ориентирование и клавиатура.** Документация различает основную область, боковые поверхности и явные элементы управления layout; скрытую вспомогательную панель можно открыть кнопкой и сочетанием. Accessibility описывает один Tab-stop для toolbar/tablist и стрелки внутри группы, видимый фокус, F6 для перехода между крупными областями и оговорку для WebView. Для Relay это принцип, а не требование перенести все комбинации: Ctrl+J уже согласован, дополнительные shortcuts сначала проверяются на конфликты сервисов. [Layout](https://code.visualstudio.com/docs/configure/custom-layout), [Accessibility](https://code.visualstudio.com/docs/configure/accessibility/accessibility).

**Vivaldi: панель как дополнительный рабочий инструмент.** EN/DE-помощь описывает постоянный вход, повторное нажатие для закрытия, отдельное закрытие панели и варианты docked/floating. Для Relay подходит docked-панель из согласованного плана. Floating поверх native-сервиса — отдельная техническая задача. Мобильный User-Agent веб-панелей Vivaldi объясняет, почему их narrow view нельзя считать проверкой настольной ленты Relay. [Paneele, DE](https://help.vivaldi.com/de/desktop-de/panels-de/paneele/), [Web Panels, EN](https://help.vivaldi.com/desktop/panels/web-panels/), [документация разработчика](https://help.vivaldi.com/developers/web/vivaldi-web-panels-for-web-developers/).

**Типографика и плотность.** Fluent использует роли и базовую иерархию 14/20 для body, 12/16 для подписи, 16/22 для небольшой секции. Это масштаб для сравнения, не причина менять существующий шрифт. В Relay подтверждены локальные Inter Variable и Unbounded. Предложение: Inter для навигации, строк, кнопок и метаданных; Unbounded — для короткого имени/характерного заголовка, где его ширина не мешает. Для длинных русских подписей и числового прогресса проверить перенос и доступное место. В исходном Titlebar имя сейчас 0.6875rem; нужный размер определяется rendered-проверкой, а не чтением CSS. [Fluent Typography](https://fluent2.microsoft.design/typography).

Предлагаемый рабочий ритм: 4/8/12/16/24 CSS px, в исходниках rem; внутри операции малый промежуток означает связанность, больший отделяет действия/элементы. Это позволяет группировать данные без одинаковых рамок вокруг каждого фрагмента. Плотность сокращает пустое место, а не скрывает объяснение ошибки. Значения являются проектным предложением. [Fluent Layout](https://fluent2.microsoft.design/layout).

Никакой отправки в аккаунт. Все варианты сохраняют Ctrl+J, панель 24rem, Current/History, ширину сервиса минимум 40rem перед переходом панели на всю рабочую область и сохранение контекста WebView. **Рекомендация для обсуждения: B + ясность результата из C.** B сохраняет привычное местоположение сервисов и подходит личному ежедневному приложению. Из C стоит взять иерархию «результат → файл → источник/формат → действия», отдельно видимые неизвестный исход и ограничение повтора. Не переносить весь квиток в постоянное широкое меню. A стоит выбрать, если пользователь часто работает в узком окне и ценит ширину ленты выше вертикальной карты; D — если главное узкое место подтверждено повторяющимся keyboard workflow. Это рекомендация автора, не решение пользователя. Выбор, сочетание и доработка требуют визуального сравнения.

**Контракт motion для прототипа.** Fluent определяет функциональные transitions и связывает длительность с масштабом/расстоянием. Прочитанный drawer-код Microsoft явно учитывает RTL и различает enter/exit easing; dialog-код использует opacity/scale-компонент. Библиотеку переносить в Teact не требуется. Значения 100–140ms ниже являются предложением Relay, а 140ms для панели уже приняты пользователем. [Fluent Motion](https://fluent2.microsoft.design/motion), [drawerMotions.ts, фиксированная ревизия](https://github.com/microsoft/fluentui/blob/4ecbb6f138784edc78b5389891fa0bad8e8afcce/packages/react-components/react-drawer/library/src/shared/drawerMotions.ts), [DialogSurfaceMotion.ts](https://github.com/microsoft/fluentui/blob/4ecbb6f138784edc78b5389891fa0bad8e8afcce/packages/react-components/react-dialog/library/src/components/DialogSurfaceMotion.ts).

- Переключение сервиса: обновление выделения/подписи без покадрового движения native-содержимого. Повторное нажатие не начинает новую цепочку эффектов.
- Открытие операций: геометрия WebView получает конечные bounds отдельно; лишь содержимое собственного DOM-панеля появляется за 140ms с opacity и малым смещением. Закрытие/повторное открытие прерывает предыдущий эффект и показывает актуальное состояние.
- Принятие операции: диалог освобождает временные данные по существующему контракту; появление реальной строки и изменение счётчика связывают действие с результатом. Декоративный полёт thumbnail поверх Instagram/X пока исключён из предложения: native airspace и lifetime Blob требуют отдельного доказательства.
- Прогресс: размер/номер элемента берутся из реального состояния. Известный объём допускает мягкое изменение fill; неизвестный объём обозначается этапом. Нет фиктивной шкалы или внезапного «100%».
- Завершение: короткая смена status-иконки и текста внутри строки. Строка/Tab-focus не прыгают из-под пользователя. Ошибка/неизвестный исход остаются читаемыми после эффекта.
- Reduced motion: все функции, focus и доступность результата работают сразу без движения; состояние не зависит от transitionend/animationend.
- Выразительный, но содержательный сложный эффект можно проверить в собственном диалоге: одинаковый media-preview связывает выбор формата и итоговую строку, в пределах одной DOM-поверхности. Он принимается только если улучшает понимание по сравнению с простым вариантом и не задерживает отправку.

**Доступность как часть композиции.** Fluent Nav предупреждает, что вторичные действия должны существовать в DOM и быть доступны вне hover. Не прятать «Отмена», «Повторить» или объяснение ошибки только в hover. Для desktop-предложения Relay разумны hit-area 32–40px; 44px для ключевого confirm/return на компактном/увеличенном интерфейсе — проектный выбор. WCAG 2.2 AA 2.5.8 устанавливает 24×24 CSS px с оговорёнными исключениями, а не универсальные 44px. Отключаемое движение рассматривается в AAA 2.3.3; reduced motion дополнительно уже является требованием Relay. [Fluent Nav](https://fluent2.microsoft.design/components/web/react/core/nav/usage/), [W3C Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [W3C Animation](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html).

**Граница native WebView.** В текущем `App.tsx` viewport измеряется через DOM и масштаб окна, bounds передаются native-командам. `multi_app.rs` отдельно создаёт, показывает и размещает native-сервисы. CSS-анимация контейнера главного DOM не доказывает синхронную анимацию дочерних native-поверхностей и не обеспечивает overlay/clip. Текущий binding `webview2-com = 0.39.1` менять ради оформления не обосновано. Официальный Controller API выделяет bounds, visibility и focus; accelerator handler имеет отдельные правила блокировки и повторных нажатий. [Microsoft Controller API, версия ссылки 1.0.4191.47](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller?view=webview2-1.0.4191.47). Страница отмечена Microsoft как legacy reference; подтверждение конкретных новых API проводится по установленным bindings перед использованием.

Практическое следствие: работать с native-поверхностью как с сохраняемым прямоугольным viewport. В своём DOM развивать typography, разделение областей, статические границы, hover/focus, диалоги, empty/error и список операций. Полноэкранная панель должна штатно скрыть native-сервис, сохранить его контекст и вернуть прежний focus. После выбора направления нужны реальные проверки Ctrl+J/Tab/Escape во всех трёх сервисах и native geometry на Windows.

**Критерии пригодности визуальных вариантов.** На каждом варианте показать одинаковые четыре состояния: чтение; confirm режима/адресата; Current со known/unknown progress; History с доступным файлом и неизвестным исходом. Дополнительно компактный 800×560, browser-layout 640×448, 200% текст, RTL и reduced motion. Подписи и главные действия должны находиться без hover и без доверия только к цвету. Не обещать hands-on motion по статичному скриншоту. После выбора измерить задержку открытия результата/переключения и непрерывность чтения; пройти те же три повтора baseline/candidate. Рекомендация не вводит новые отправки, аккаунты, зависимости или облачные функции.
