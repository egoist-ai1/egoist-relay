# Telegram: соединение Relay через работающий Lagom без VPN

Дата проверки: 30 сентября 2026 года. Проверки не использовали аккаунты, завершение обмена ключами, QR-авторизацию или пользовательские сообщения.

Браузерный GramJS использует WebSocket с обфускацией TCP abridged. Lagom tg-ws-proxy 1.7.0 принимает TCP MTProxy и сам выбирает исходящий маршрут Telegram. Прямое направление браузерного WebSocket на порт MTProxy несовместимо с этим протоколом.

`scripts/telegram-transport.mjs` предоставляет локальный адаптер: браузерный WebSocket → преобразование транспортной обфускации AES-CTR → существующий TCP MTProxy Lagom. Формат abridged сохраняется. Адаптер не разбирает сообщения MTProto, не выполняет вход в аккаунт и не расшифровывает данные, защищённые ключом аккаунта. Он не создаёт VPN, DNS-службу или DPI-движок и не выбирает внешние маршруты вместо Lagom.

## Обнаружение и запуск

Конфигурация читается из защищённого каталога Lagom `ProgramData/EgoistShield/Runtime/TelegramProxy/config.json` при запуске и каждом новом соединении. Адрес и порт берутся из файла. Поддерживаются только loopback-адреса и корректный MTProxy-ключ. Конфигурация и ключ не сохраняются в Relay и не передаются браузеру, аргументам запуска или журналу адаптера. При аудите фактический listener сверён с процессом tg-ws-proxy и его SCM wrapper; при запуске адаптер проверяет защищённый путь, формат конфигурации и доступность указанного loopback listener.

Существующий listener проверяется коротким TCP-соединением без полезной нагрузки с пределом 1200 мс. При недоступной или некорректной конфигурации дочерний процесс возвращает `{"status":"unavailable"}` и завершается с кодом 0. Доступность listener сама по себе не означает, что внешний маршрут Telegram исправен: это отдельно подтверждено публичным ReqPQ ниже.

Первой строкой stdin передаются `{token, origins, port?}`. Токен — 64 шестнадцатеричных символа; разрешённые источники задаёт нативный код. Основной источник Windows — `http://tauri.localhost`; `http://localhost:1234` предназначен для отладки. Адаптер слушает `127.0.0.1`, первоначально на свободном порту. Необязательный `port` позволяет восстановить тот же адрес после перезапуска дочернего процесса. Единственный ответ успешного запуска содержит `status: "ready"` и локальный URL с токеном. Закрытие stdin останавливает соединения и процесс.

Поддерживаются DC 1–5; параметр `media=1` передаёт отрицательный номер DC. `premium=1` использует базовый DC. Это подтверждает работоспособность такого соединения, но не гарантирует возможности отдельного premium WebSocket-маршрута. `test=1` отклоняется: tg-ws-proxy 1.7.0 не предоставляет соответствующий режим WebSocket; вызывающий код должен сохранять официальный маршрут тестового сервера.

## Проверки через реальный Lagom

Ожидаемый ответ — `ResPQ` с конструктором `0x05162463`, совпадающим случайным nonce, нулевым `auth_key_id` и корректной длиной тела. Обмен прекращался сразу после проверки ответа: ключ авторизации не создавался.

| Путь | Условия | Результат |
| --- | --- | --- |
| TCP MTProxy Lagom | DC2, без Relay-адаптера | Корректный ResPQ, 720 мс |
| TCP MTProxy Lagom | DC4, без Relay-адаптера | Корректный ResPQ, 560 мс |
| WebSocket → production source адаптера → Lagom | DC2, заголовок и пакет разбиты на части | Корректный ResPQ, 741 мс |
| WebSocket → production source адаптера → Lagom | DC4, заголовок и пакет вместе, `premium=1` | Корректный ResPQ, 801 мс |
| WebSocket → production source адаптера → Lagom | DC5 | Корректный ResPQ, 847 мс |
| WebSocket → production source адаптера → Lagom | DC2, `media=1`, заголовок и пакет вместе | Корректный ResPQ, 583 мс |
| WebSocket → собранный CJS-адаптер → Lagom | DC2 | Корректный ResPQ, 325 мс |

При первом обращении к DC5 ответ занял 11 713 мс; при повторной проверке — 847 мс. Начальная задержка исходящего маршрута Lagom возможна; эти измерения не являются гарантией пропускной способности или времени авторизации.

## Проверки доступа и жизненного цикла

- HTTP 403 для неверного/отсутствующего Origin или токена, другого WebSocket-подпротокола, DC вне диапазона, тестового режима, повторного/неизвестного параметра и другого пути.
- Соединение закрывается для текстового кадра, некорректного заголовка обфускации и кадра больше 4 МиБ.
- Соединения ограничены 128; буферы ограничены 8 МиБ; включены обратное давление, контроль pong, сроки ожидания заголовка, ответа и освобождения буфера.
- Собранный CJS-процесс закрыл активный WebSocket и завершился с кодом 0 после EOF stdin. Последующий запуск восстановил тот же локальный порт и URL.
- Локальный стенд с отдельно сгенерированными ключами подтвердил перечитывание порта/ключа без перезапуска и правильный отрицательный DC для медиа. Рабочая конфигурация Lagom не копировалась и не изменялась.
- Некорректные адрес, порт или ключ отклонены. Отсутствующая конфигурация дала единственный ответ `unavailable`, пустой stderr и код завершения 0 за 52 мс.

`scripts/build-telegram-transport.mjs --outfile <absolute-path>` собирает CJS с существующими `ws` и `esbuild`. Сохранён полный MIT license установленного `ws`; необязательные нативные расширения отключены при сборке. Проверки синтаксиса исходников и сборка завершились успешно. Постоянные тесты в проект не добавлялись; стенды и полные обезличенные результаты находятся в runtime выполняющей задачи.

## Границы проверки и источники

Эти проверки подтверждают преобразование транспорта и начальную доступность Telegram через существующий Lagom. Полный обмен ключами, появление QR в нативном приложении, авторизация Instagram/X и проверка упакованного Relay относятся к отдельной интеграционной проверке. Данные существующих аккаунтов не использовались.

Контракт протокола проверен по [исходнику tg-ws-proxy v1.7.0](https://github.com/Flowseal/tg-ws-proxy/blob/v1.7.0/proxy/tg_ws_proxy.py), [транспортному мосту этой версии](https://github.com/Flowseal/tg-ws-proxy/blob/v1.7.0/proxy/bridge.py) и [официальному примеру ReqPQ Telegram](https://core.telegram.org/mtproto/samples-auth_key). В версии 1.7.0 принимаются abridged, intermediate и padded intermediate; ключ транспортного шифра MTProxy вычисляется как SHA256 от prekey и секрета. Совместимость abridged с установленным бинарным runtime подтверждена непосредственным обменом; точное соответствие бинарного файла опубликованному исходнику из этого результата не следует.
